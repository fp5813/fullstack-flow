# Phase 4: 实施计划

> 在写代码前，将规格分解为可执行的任务清单。

## 快速概览

```
Step 0 读取状态 → Step 1 定位规格 → Step 2 任务分解（T001+）
  → Step 2.5 测试验证计划 → Step 3 排序 + 风险预评估
  → Step 4 更新索引 → Phase 出口 → coverage-check
```

**核心**: T### [P] 原子任务 + 测试验证计划 + AC 映射 + 风险预评估（7 类风险）

## 职责

**输入**：规格文档（`docs/规格文档/`）  
**输出**：`docs/实施计划/YYYY-MM-DD-{功能简述}.md`  
**模式**：只读（不写代码）

## 流程

### Step 0: 入口（Read `scripts/phase-entry-exit.md` 入口流程）

- parameters: current_phase="plan", next_phase="coverage-check"
- 额外：验证前置制品 `artifacts.spec.path` 存在

### Step 1: 定位并理解规格文档

提取修改目标、影响范围文件、验收标准。

### Step 2: 任务分解

格式：`T### [P] {任务描述} — \`path/to/File\`  [AC01, AC02]`

分解原则：
1. **原子性** — 一个任务只做一件事
2. **可验证** — 完成后有明确验证方式
3. **有依赖** — 标注前后关系
4. **有 AC 映射** — 每个任务标注覆盖的 AC 编号

### Step 2.5: 生成测试验证计划

基于规格文档中的"方案设计与验证策略"章节，生成独立的测试验证计划：

#### 2.5.1 提取验证要素

从规格文档提取：
- **条件分支矩阵**中的每个条件→处理→验证映射
- **测试数据类型清单**中的每类数据及其覆盖场景
- **AC 清单**中的每个验收标准

#### 2.5.2 生成测试验证任务

将验证要素映射为具体的测试任务，追加到任务清单：

| 测试任务 | 验证内容 | 数据类型 | 依赖 | 关联 AC |
|---------|---------|---------|:----:|:-------:|
| V001 | {验证内容描述} | {正常/边界/异常/枚举} | T{实现任务} | AC01 |
| V002 | {验证内容描述} | {边界数据} | T{实现任务} | AC02 |

**测试任务命名规范**：
- 编号：`V###`（从 V001 递增），与 T### 任务在同一清单中混合编号
- 类型：标注为"测试"
- 依赖：标注依赖的实现任务编号（测试必须在实现之后执行）

**验证内容覆盖要求**：

| 覆盖维度 | 要求 | 对应来源 |
|---------|------|---------|
| 条件分支全覆盖 | 条件分支矩阵中的每行至少对应 1 个 V### 任务 | 条件分支矩阵 |
| 数据类型全覆盖 | 测试数据类型清单中的每类数据至少 1 个 V### 任务 | 测试数据类型清单 |
| AC 全覆盖 | 每个 AC 至少 1 个 V### 任务 | AC 清单 |
| 异常流程覆盖 | 参数校验失败、业务异常、权限不足至少各 1 个 | 经验规则 |

#### 2.5.3 测试任务模板

```markdown
### V001: {验证内容}
- **类型**: 测试
- **验证方式**: API 调用 / 数据库查询 / 属性测试
- **测试数据**: {引用测试数据类型清单中的具体数据类型}
- **前置条件**: {需要先完成的实现任务}
- **预期结果**: {期望的响应或数据状态}
- **关联 AC**: AC01
```

### Step 3: 排序 + 风险预评估

排序：后端先行、风险先行、独立先行。

风险预评估（在分解任务后，逐项评估）：

| 风险类别 | 检查项 | 级别判定 | 应对策略 |
|---------|--------|---------|---------|
| **技术风险** | 涉及不熟悉的技术栈、第三方库、新框架？ | 高/中/低 | 追加 Spike 任务（技术调研单独成任务） |
| **兼容性风险** | 修改是否影响现有 API 响应格式、数据库表结构、前端接口？ | 高/中/低 | 向后兼容方案（版本路由/字段兼容） |
| **数据风险** | 涉及数据迁移、表结构变更、历史数据兼容？ | 高/中/低 | 迁移脚本 + 回滚脚本 + 数据校验 |
| **依赖风险** | 任务依赖未完成的第三方接口、未合并的 PR、外部系统？ | 高/中/低 | Mock 接口 / 标记阻塞 |
| **回退复杂度** | 修改失败后回退的难度（涉及文件数、API 变更数、数据变更数） | 高/中/低 | 步骤化回退方案，每个任务对应独立回退 |
| **范围蔓延** | 任务是否超出规格 Scope？是否存在"顺手修复"诱惑？ | ⚠️ 标记 | 超出部分单独开新任务，不进本次计划 |
| **测试数据覆盖** | 规格文档中列出的测试数据类型（正常/边界/异常/枚举）是否都有对应任务覆盖？ | 高/中/低 | 不足时追加测试数据准备任务 |

**高风险判定**：任一风险为"高"时，实施计划尾部追加"风险应对"子章节，描述具体应对方案。

**低风险判定**：所有风险"低"时，可跳过风险应对子章节。

### Step 4: 用户确认实施计划

实施计划生成后，向用户展示关键内容并请求确认：

```markdown
**请确认实施计划：**

**任务清单：**
| ID | 任务 | 类型 | 文件 | AC | 预估 |
|----|------|:----:|------|:--:|:----:|
| T001 | {描述} | 后端 | `path` | AC01 | 10min |
| V001 | {验证} | 测试 | `tests/...` | AC01 | 10min |

**测试验证计划：**
| 测试任务 | 验证方式 | 测试数据 | 前置条件 |
|---------|---------|---------|:--------:|
| V001 | API 调用 | {数据类型} | T001 |
| V002 | 数据库查询 | {边界数据} | T001 |

**风险评估：**
| 类别 | 级别 | 影响 |
|------|:----:|------|
| 技术风险 | {高/中/低} | {说明} |

**业务流程修改确认：**
1. **修改点**: {具体修改的业务逻辑}
2. **影响范围**: {涉及的文件/功能}
3. **风险项**: {高风险项及应对方案}

请确认 (yes/no/修改建议)：
```

| 用户反馈 | 处理方式 |
|---------|---------|
| 确认 | 进入 Step 5 更新索引 |
| 调整顺序/拆分任务 | 更新计划后重新展示 |
| 指出遗漏风险 | 补充风险评估后重新展示 |
| 不同意修改方案 | 回退 Phase 3 重新确认规格 |

> **核心原则**：所有修改代码前，必须经过用户确认实施计划，用户对任务拆分、顺序和风险有最终决定权。

### Step 5: 更新实施计划索引（Read `scripts/update-index.md`）

执行 prepend 模式：
- index_path: "docs/实施计划/INDEX.md"
- row_content: "| {日期} | [{简述}](./{文件名}) | {任务数} 个任务 |"

### Step 6: Phase 出口（Read `scripts/phase-entry-exit.md` 出口流程）

1. 如有设计决策被用户确认，Read `scripts/create-decision.md` 创建决策日志
2. 更新 `artifacts.plan.path`, `artifacts.plan.updated_at`
3. 参数: current_phase="plan", next_phase="coverage-check"

## 自检

- [ ] 每任务一个职责（原子性）
- [ ] 任务编号从 T001 递增
- [ ] [P] 标记的任务确实可并行（不同文件、无依赖）
- [ ] 所有 AC 被任务 100% 覆盖（实现 + 验证）
- [ ] 单任务预估 ≤ 30 分钟
- [ ] 依赖关系正确（无循环依赖）
- [ ] 风险预评估已完成（6 类风险逐项检查）
- [ ] 测试数据覆盖风险已评估（规格文档中的测试数据类型清单有对应任务）
- [ ] 条件分支全覆盖（条件分支矩阵每行有对应 V### 任务）
- [ ] 数据类型全覆盖（测试数据类型清单每类有对应 V### 任务）
- [ ] 实施计划已获用户确认
- [ ] 风险评估已获用户确认

## 约束

- 绝不写代码。不做技术选型。标注依赖关系。每任务 ≤ 30 分钟。
- **用户确认前置**：Step 4 未获用户确认实施计划不得进入 Phase 5（编码）
